1. The idea in simple words

Every time a visitor opens a page, the shop could ask the database in Singapore for the products and build the page. That is slow when nobody has asked recently, and wasteful when a hundred people ask for the same page. The better way: build the page once, keep a copy close to the visitor, and rebuild it only when something changes. The database stays the one true record; the copies are only photocopies.

Your suggestion, in this vocabulary: “prepare the first one or two pages in advance near Lahore, load the next pages as people scroll, and refresh the copy when someone buys or an admin edits.” That is exactly the standard pattern. The one change we recommend is the order of the refresh (next section).

Layers 1 and 2 already remove most database visits for public pages. Layers 3 and 4 matter once there are hundreds of products, or when pages differ by filter and sort.

4. Prices, stock and orders: how we stay honest

  • A page can be up to about a minute old. Prices, “in stock” and flash-sale labels on pages come from the copy.
  • The server never trusts the page. When the shopper adds to the bag and again at checkout, the real database is asked, and the price is recalculated on the server.
  • Stock is protected in the database, not in the copy. An order holds stock with an atomic update; two people cannot buy the last item.
  • When the owner edits something, the admin tells the shop to throw away its saved pages (“purge”), so the change shows in seconds on the nearest copy and within about 45 seconds elsewhere.
  • When someone buys, stock changes in the database first; the copies catch up within the same window. A sold-out item may show for up to a minute but cannot be ordered.

The admin site

The admin never saves pages (they are private and change all day). It does have its own Cloudflare timer (admin-entry.ts, every 3 minutes) that asks for the health check and the sign-in page, so the database and the admin code are awake when the owner opens the panel. On 8 October the owner noticed the first admin page of the day was slow while a simple page was fast; this is the fix.

7. Plan

  1. Now (built): page copies in the visitor’s data centre, Cloudflare timer, lighter first load. Measure after the merge: look for the x-edge-cache header (HIT, STALE, MISS).
  2. After launch, two weeks of numbers: hit rate, time to first byte from Lahore, database wake-ups.
  3. If still slow: product snapshot (layer 3) and cached product pages API (layer 4); then Smart Placement test; then a region decision.
